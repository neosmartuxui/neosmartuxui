## Admission rules

A candidate becomes a separate Core ID only when it is domain-free, behaviorally distinct, reusable across multiple verticals, and not merely a variant, subpart, preset, or thin composition of existing primitives.

Decision meanings:

- **Core** — approve as a separate generic capability, subject to contract review.
- **Merge** — implement as capability/state of another Core component and do not count separately.
- **Block** — composition belongs in v0.5 Core Blocks rather than generic Core.
- **Vertical** — domain semantics belong in a vertical package.
- **Defer** — potentially generic, but not required in the first expansion wave; research before ID freeze.

### Expansion A2 repository-reality correction

During contract freeze, the canonical `core.select` documentation and validator were re-read. They explicitly require a **real native single-select `<select>`**. Therefore the earlier A1 assumption that NativeSelect was distinct from a custom Select was wrong for NeoSmartUI's actual repository. `NativeSelect` is merged into existing `core.select`, no `core.native-select` ID is created, and `core.number-field` takes its place in the first contract batch. This correction is count-integrity work, not a scope expansion.

### Expansion B repository-reality correction

Before the second Forms/Selection contract freeze, the shipping `core.input`, `core.input-group`, and `core.radio` boundaries were re-read.

- `core.input` already explicitly supports native `<input type="search">`, while `core.input-group` plus ordinary Buttons owns generic clear/submit adornments. Therefore **SearchField is merged** into those existing capabilities and no `core.search-field` ID is created.
- `core.radio` already owns mutually-exclusive choice semantics, native Arrow/Space behavior, checked state, minimum effective targets, and explicitly treats alternate choice-card presentation as composition. Therefore **Rating is merged** into `core.radio` plus presentation/labels and no `core.rating` ID is created.

These are count-integrity corrections, not reductions in usable product capability.

## Sixth Expansion C contract slice

The next dependency is one contract-only menu-button primitive:

1. `core.dropdown-menu`

Repository-reality boundaries are frozen before implementation:

- DropdownMenu is an explicitly invoked temporary `role="menu"` surface opened by one native menu button with `aria-haspopup="menu"`, `aria-expanded`, and an explicit controlled-menu relationship.
- DropdownMenu is not Popover: opening moves focus into a managed menu-item composite with arrow/Home/End/typeahead navigation and menu-item activation semantics.
- DropdownMenu is not Select/Listbox/Combobox: menu items invoke actions/commands or explicit checkable menu-item state rather than committing a generic value option.
- DropdownMenu is not ContextMenu: right-click, long-press, `Shift+F10`, and context-menu-key invocation are outside this trigger contract.
- DropdownMenu is not Menubar or NavigationMenu: it is temporary, owned by one menu button, and does not own persistent horizontal menu navigation or site/application route hierarchy.
- This first contract freezes one menu surface; nested submenu orchestration and Left/Right submenu traversal are not silently included.
- Canonical contract states are exactly `closed`, `open`, `hover`, `focus-visible`, `pressed`, `checked`, and `disabled`.
- Enter/Space/ArrowDown/ArrowUp can open from the trigger and establish deterministic menu-item focus; ArrowUp/Down wrap, Home/End jump, and printable-character typeahead moves focus by accessible name.
- Escape closes and restores trigger focus. Tab/Shift+Tab close without trapping or preventing ordinary document traversal.
- Disabled menu items remain focus-discoverable but inert. Plain menu-item activation closes/restores; checkable menu-item activation updates checked state while keeping the menu open.
- Pointer/touch activation follows the same semantic item path; outside activation light-dismisses without stealing outside focus.
- Context-menu/right-click/long-press invocation remains reserved for the later `core.context-menu` contract.
- DropdownMenu owns interaction semantics, not business command execution, network/form authority, application scheduling, or routing/navigation policy.
- Contract-only admission originally left the deployed/public Theme boundary at 40 Core / 55 semantic tokens and the 228-state shipping preview matrix unchanged; implementation later advanced the maintained local scope to 41 Core / 55 tokens and the shipping preview matrix to 235 states under exact-set maintenance before deployment.

## Seventh Expansion C contract slice

The next dependency is one contract-only context-invoked menu primitive:

1. `core.context-menu`

Repository-reality boundaries are frozen before implementation:

- ContextMenu is a temporary `role="menu"` surface invoked from one explicit context target rather than from a menu button.
- Pointer/context invocation is authoritative: a `contextmenu` event on the bound target may open the custom menu at the invocation coordinates. The adapter MUST NOT suppress the browser context menu outside an explicitly bound valid target.
- Keyboard context invocation is authoritative: `Shift+F10` and the platform `ContextMenu` key on the focused context target open the same menu and establish menu-item focus.
- The context target must already be keyboard reachable through correct host semantics; ContextMenu MUST NOT manufacture `tabindex`, role, click behavior, or ordinary primary-button activation on the target.
- Touch long-press is first-class ContextMenu invocation. A future adapter may consume platform `contextmenu` or use a deliberate hold gesture, but a synthetic hold must cancel on meaningful movement, scroll/pointer cancellation, or early release; ordinary tap and nested editable/text-selection authority remain native.
- ContextMenu is an enhancement rather than the only discoverability path for an essential action; required operations must also have an ordinary visible/keyboard-discoverable application path.
- ContextMenu is not DropdownMenu: it has no menu-button trigger, no primary-click disclosure contract, and no `aria-expanded` button authority.
- ContextMenu is not generic Popover: once open, the surface owns menu roles, managed item focus, arrow/Home/End/typeahead navigation, item activation, and dismissal.
- ContextMenu is not Menubar or NavigationMenu: it is temporary and context-specific rather than a persistent command bar or route hierarchy.
- ContextMenu is not Select/Listbox/Combobox and does not turn menu actions into generic form/value options.
- The first slice freezes one menu surface. Nested submenu orchestration and Left/Right submenu traversal are deferred within the menu family rather than split into count-inflating aliases.
- Canonical contract states are exactly `closed`, `open`, `hover`, `focus-visible`, `pressed`, `checked`, and `disabled`; pointer coordinates, invocation modality, anchor geometry, active index, typeahead buffer, and animation phase are runtime details rather than component-state IDs.
- Opening moves DOM focus to a menu item. ArrowUp/Down wrap, Home/End jump, printable typeahead moves by accessible name, and disabled items remain focus-discoverable but inert.
- `Escape` closes and restores focus to the invoking context target. `Tab`/Shift+`Tab` close without trapping or preventing ordinary document traversal.
- Plain menu-item activation emits only a local interaction signal, closes, and restores the invoking context. Checkable items may update explicit checked state while keeping the menu open.
- Outside pointer activation light-dismisses without stealing focus from the newly activated outside target.
- ContextMenu owns context invocation and menu interaction semantics only. It does not execute business commands, navigate, submit forms, perform network work, schedule application work, or replace browser context menus globally.

## Eighth Expansion C contract slice

The next dependency is one contract-only persistent application-command menu primitive:

1. `core.menubar`

Repository-reality boundaries are frozen before implementation:

- Menubar is a persistent, normally horizontal `role="menubar"` composite for domain-free application commands. It MUST have an explicit accessible name through `aria-label` or `aria-labelledby`.
- Root items use `menuitem`, `menuitemcheckbox`, or `menuitemradio`; passive separators never enter the focus model. Exactly one valid root item participates in ordinary document Tab order at a time.
- `Tab` and `Shift+Tab` enter or leave the Menubar as one composite stop. Re-entry restores the last valid root item when available, otherwise the first root item. Menubar MUST NOT trap document focus.
- Root `ArrowLeft`/`ArrowRight` traversal wraps among root items; RTL reverses the visual direction mapping without reordering DOM command semantics. `Home`/`End` move to the first/last root item in document order, and printable-character typeahead moves by accessible name.
- Disabled root/submenu items remain focus-discoverable with `aria-disabled="true"` but activation is inert. Checkable items expose explicit `aria-checked`.
- A root item that owns a first-level submenu exposes `aria-haspopup="menu"` and `aria-expanded`. `Enter`, `Space`, or `ArrowDown` opens at the first submenu item; `ArrowUp` may open at the last submenu item.
- A first-level submenu is a vertical `role="menu"` composite. `ArrowUp`/`ArrowDown` wrap, `Home`/`End` jump, printable typeahead moves by accessible name, and `Escape` closes the submenu and restores focus to its owning root item.
- At most one first-level submenu is open. While one is open, root Left/Right traversal closes or transfers that submenu deterministically to the newly focused root peer; a peer without a submenu leaves no submenu open.
- `Tab` or `Shift+Tab` from any open submenu closes it and permits ordinary document traversal; Menubar MUST NOT create a modal or focus trap.
- Plain enabled item activation emits only a local interaction signal. Checkable activation may update local checked state. Core does not execute business commands, navigate, submit forms, perform network work, schedule application work, or mutate application-owned state.
- Pointer/touch primary activation follows the same semantic item path. Hover may style an item but MUST NOT execute commands or silently move DOM focus; right-click, long-press, `Shift+F10`, and the platform ContextMenu key remain ContextMenu authority.
- Menubar is not DropdownMenu: the root composite is persistent rather than opened by one menu button. Menubar is not ContextMenu: it has no contextual invocation target. Menubar is not generic Popover: menu roles/focus are intrinsic. Menubar is not Toolbar: it contains menu items rather than arbitrary controls.
- Menubar is not NavigationMenu: it does not own site/application route hierarchy, destination disclosure, current-route state, or navigation policy. Those semantics remain reserved for the next `core.navigation-menu` contract.
- Menubar is not Select/Listbox/Combobox and is not searchable CommandMenu; command activation does not become generic value selection or text-filter authority.
- The first Menubar slice permits one first-level submenu only. Nested submenus inside first-level menus are deferred reviewed menu-family capability rather than split into count-inflating aliases.
- Canonical contract states are exactly `closed`, `open`, `hover`, `focus-visible`, `pressed`, `checked`, and `disabled`; active root index, last-focused root, submenu anchor geometry, typeahead buffer, RTL traversal mapping, and animation phase are runtime details rather than additional component-state IDs.

- Contract-only admission originally left deployed/public Theme authority at **42 Core / 55 semantic tokens** and the **242-state shipping preview matrix** unchanged. ## Ninth Expansion C contract slice

The next dependency is one contract-only site/application navigation disclosure primitive:

1. `core.navigation-menu`

Repository-reality boundaries are frozen before implementation:
